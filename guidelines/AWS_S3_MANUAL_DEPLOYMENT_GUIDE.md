# AWS Manual Production Deployment Guide

This guide deploys the A Muslim Matchmaker admin dashboard manually to AWS at:

```txt
https://admin.amuslimmatchmaker.com
```

There is no CI/CD in this setup. Each release is built on a trusted local computer, uploaded to Amazon S3, and refreshed in Amazon CloudFront.

The production architecture is:

```txt
Browser
  -> DNS: admin.amuslimmatchmaker.com
  -> Amazon CloudFront: HTTPS, SSL/TLS, caching, HTTP-to-HTTPS redirect
  -> Private Amazon S3 bucket: compiled Vite files from dist/
```

This is intentionally different from exposing an S3 static website endpoint directly. S3 website endpoints do not provide HTTPS for a custom domain. CloudFront provides the custom domain and HTTPS, while Origin Access Control (OAC) allows the S3 bucket to remain private.

## Final Configuration Summary

Use these values throughout the guide:

```txt
Application domain: admin.amuslimmatchmaker.com
AWS region for the S3 bucket: eu-north-1 (Europe/Stockholm)
AWS region for the ACM certificate: us-east-1 (mandatory CloudFront exception)
S3 public access: blocked
S3 static website hosting: disabled/not required
CloudFront origin type: regular S3 bucket origin, not an S3 website endpoint
CloudFront origin access: Origin Access Control (OAC)
CloudFront viewer protocol: Redirect HTTP to HTTPS
Build command: npm run build
Build output: dist/
Production API: https://api.amuslimmatchmaker.com/api
Deployment method: manual AWS CLI or manual AWS Console upload
```

Replace these placeholders whenever they appear:

```txt
YOUR_BUCKET_NAME       A globally unique S3 bucket name
YOUR_AWS_ACCOUNT_ID    The 12-digit AWS account ID
YOUR_DISTRIBUTION_ID   The CloudFront distribution ID
```

A suitable bucket name is:

```txt
amm-admin-dashboard-prod-YOUR_AWS_ACCOUNT_ID
```

The bucket name does not need to match the public domain because users access CloudFront, not S3 directly.

## Important Security Model

The files generated by Vite are public frontend files. Authentication and authorization must still be enforced by the backend API. Hiding the S3 bucket does not make JavaScript, HTML, images, or Vite environment variables secret; browsers must download them to run the application.

Never put any of the following in a `VITE_` environment variable:

- AWS access keys or secret keys
- Database credentials
- Private API keys
- Backend secrets
- Admin passwords or tokens

The S3 bucket must contain only deployable frontend files. Do not upload source code, `.env` files, credentials, private documents, or database exports.

## Before Starting

Confirm that you have:

- Access to the AWS account that will own S3, CloudFront, and the ACM certificate.
- Permission to manage DNS for `amuslimmatchmaker.com`.
- Permission to create an S3 bucket, CloudFront distribution, CloudFront Function, OAC, ACM certificate, and relevant IAM/bucket policies.
- Node.js and npm installed locally.
- AWS CLI installed and authenticated if using the recommended CLI deployment workflow.
- The backend prepared to accept requests from `https://admin.amuslimmatchmaker.com`.

Check the local tools:

```powershell
node --version
npm --version
aws --version
aws sts get-caller-identity
```

`aws sts get-caller-identity` should return the expected AWS account before any upload is performed.

## Step 1: Prepare Production Environment Variables

Create or update `.env.production` in the project root:

```env
VITE_API_BASE_URL=https://api.amuslimmatchmaker.com/api
```

The application currently has the same API URL as a code fallback, but explicitly setting it for a production build makes the intended target clear.

Vite reads `.env.production` during `npm run build` and embeds the values in the generated JavaScript. S3 and CloudFront do not read `.env.production` at runtime. Every environment-variable change therefore requires a new build and upload.

Ensure these entries are ignored by Git:

```gitignore
.env
.env.local
.env.*.local
dist
```

It is acceptable to commit an `.env.example` containing only non-secret placeholders.

## Step 2: Build and Test Locally

From the project root, perform a reproducible installation and build:

```powershell
npm ci
npm run build
```

Use `npm ci` when `package-lock.json` is present. It installs exactly the dependency versions recorded in the lock file. Use `npm install` only when intentionally changing dependencies or the lock file.

The build must create:

```txt
dist/
  index.html
  assets/
  ...
```

Optionally preview the exact production output:

```powershell
npx vite preview
```

Test login and major pages locally. Stop the preview server before continuing.

Only the contents of `dist/` will be deployed. The correct S3 layout is:

```txt
s3://YOUR_BUCKET_NAME/index.html
s3://YOUR_BUCKET_NAME/assets/...
```

Do not upload the `dist` directory as an extra level:

```txt
s3://YOUR_BUCKET_NAME/dist/index.html   # Incorrect
```

## Step 3: Create the Private S3 Bucket

In the AWS Console:

1. Open **S3** and choose **Create bucket**.
2. Select **Europe (Stockholm) `eu-north-1`**. This keeps the frontend bucket in the same AWS region as the project's backend and related infrastructure.
3. Enter the globally unique bucket name chosen earlier.
4. Leave **Object Ownership** as **ACLs disabled / Bucket owner enforced**.
5. Leave all four **Block Public Access** settings enabled.
6. Keep default encryption enabled. **SSE-S3** is sufficient for these frontend assets.
7. Enable **Bucket Versioning** if easy rollback of overwritten or deleted files is desired. It is recommended for production, although it adds some storage cost.
8. Create the bucket.

Do **not** enable S3 Static Website Hosting. CloudFront will use the S3 REST endpoint with OAC. Do **not** add a public-read bucket policy, and do **not** disable Block Public Access.

The bucket can also be created with the CLI:

```powershell
aws s3api create-bucket --bucket YOUR_BUCKET_NAME --region eu-north-1 --create-bucket-configuration LocationConstraint=eu-north-1
aws s3api put-public-access-block --bucket YOUR_BUCKET_NAME --public-access-block-configuration BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true
```

To enable versioning:

```powershell
aws s3api put-bucket-versioning --bucket YOUR_BUCKET_NAME --versioning-configuration Status=Enabled
```

## Step 4: Request the SSL/TLS Certificate in ACM

The S3 bucket and the project's other infrastructure remain in **Europe (Stockholm), `eu-north-1`**. However, CloudFront can use an AWS Certificate Manager certificate only when the certificate is in **US East (N. Virginia), `us-east-1`**. The certificate is the only resource in this guide that must use `us-east-1`; creating it in `eu-north-1` will prevent it from being selected in CloudFront.

1. Open **AWS Certificate Manager (ACM)**.
2. Change the console region to **US East (N. Virginia) `us-east-1`**.
3. Choose **Request certificate**.
4. Choose **Request a public certificate**.
5. Enter exactly:

   ```txt
   admin.amuslimmatchmaker.com
   ```

6. Select **DNS validation**.
7. Keep the recommended key algorithm and request the certificate.
8. Open the certificate and locate the DNS validation CNAME name and value.

### If DNS Is Hosted in Route 53

Choose **Create records in Route 53**, verify the selected hosted zone, and allow ACM to create the validation record.

### If DNS Is Hosted Elsewhere

At the current DNS provider, create the CNAME shown by ACM exactly as provided:

```txt
Type: CNAME
Name/Host: the ACM validation name
Value/Target: the ACM validation value
TTL: 300 seconds, or the provider default
```

Some DNS interfaces automatically append `amuslimmatchmaker.com`. If so, enter only the host portion that the interface expects and verify that the resulting fully qualified record matches ACM.

Wait until ACM shows:

```txt
Status: Issued
```

Do not delete the ACM validation CNAME after issuance. ACM uses it for automatic certificate renewal.

## Step 5: Create the CloudFront Distribution and OAC

1. Open **CloudFront** and choose **Create distribution**.
2. For **Origin domain**, select the regular S3 bucket created earlier.
3. Confirm that the origin resembles:

   ```txt
   YOUR_BUCKET_NAME.s3.eu-north-1.amazonaws.com
   ```

   Do not enter an `s3-website-...amazonaws.com` endpoint.

4. For **Origin access**, select **Origin access control settings (recommended)**.
5. Create a new OAC if necessary:
   - Give it a descriptive name such as `amm-admin-dashboard-oac`.
   - Keep **Sign requests** enabled.
   - Save/select the OAC.
6. If CloudFront offers to update the S3 bucket policy automatically, allow it. If it only displays a policy, copy it and add it to the S3 bucket after the distribution is created.
7. Under **Default cache behavior**:
   - Viewer protocol policy: **Redirect HTTP to HTTPS**.
   - Allowed HTTP methods: **GET, HEAD**.
   - Compress objects automatically: **Yes**.
   - Cache policy: **CachingDisabled**. A separate optimized behavior for hashed assets is added later.
   - Do not forward cookies, authorization headers, or query strings to S3; the frontend files do not need them.
8. Set **Default root object** to:

   ```txt
   index.html
   ```

9. Under **Alternate domain name (CNAME)**, add:

   ```txt
   admin.amuslimmatchmaker.com
   ```

10. Under **Custom SSL certificate**, choose the ACM certificate issued in the previous step.
11. Select the current recommended TLS security policy offered by CloudFront. Do not enable obsolete SSL/TLS protocol versions for legacy clients unless there is a documented requirement.
12. Enable HTTP/2 and HTTP/3 if offered.
13. Leave AWS WAF disabled initially unless a WAF policy and its additional cost are intentionally required.
14. Create the distribution.

CloudFront deployment can take several minutes. Record both values:

```txt
Distribution ID: for example E1234567890ABC
Distribution domain: for example d123example.cloudfront.net
```

### Verify the Private Bucket Policy

The S3 bucket policy should grant `s3:GetObject` only to the CloudFront service and only from this distribution. It should follow this structure:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowCloudFrontServicePrincipalReadOnly",
      "Effect": "Allow",
      "Principal": {
        "Service": "cloudfront.amazonaws.com"
      },
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::YOUR_BUCKET_NAME/*",
      "Condition": {
        "StringEquals": {
          "AWS:SourceArn": "arn:aws:cloudfront::YOUR_AWS_ACCOUNT_ID:distribution/YOUR_DISTRIBUTION_ID"
        }
      }
    }
  ]
}
```

Use the policy generated by CloudFront when available because it contains the exact account, distribution, and bucket values. The bucket must still show **Block all public access: On**.

## Step 6: Add SPA Routing with a CloudFront Function

This project uses browser-history routes such as `/login`, `/users`, `/users/123`, `/matches`, and `/settings`.

S3 contains `index.html`, not physical files at those paths. A direct refresh on `/users/123` would therefore fail unless the request is rewritten to `/index.html`.

Use a CloudFront Function instead of converting every S3 403/404 into `index.html`. A blanket error conversion can hide genuinely missing JavaScript, CSS, or image files by returning HTML for them.

1. In CloudFront, open **Functions**.
2. Choose **Create function**.
3. Name it `amm-admin-spa-rewrite`.
4. Use the latest available CloudFront Functions JavaScript runtime.
5. Replace the function code with:

   ```javascript
   function handler(event) {
     var request = event.request;
     var uri = request.uri;

     if (uri.endsWith('/') || !uri.includes('.')) {
       request.uri = '/index.html';
     }

     return request;
   }
   ```

6. Save the function.
7. Test paths such as:

   ```txt
   /login          -> /index.html
   /users/123      -> /index.html
   /settings/      -> /index.html
   /assets/app.js  -> /assets/app.js
   ```

8. Publish the function. A saved development version cannot be associated with production traffic.
9. Associate it with the distribution:
   - Distribution behavior: **Default (`*`)**.
   - Event type: **Viewer request**.
10. Save and wait for the distribution change to deploy.

## Step 7: Configure Efficient Caching

Vite creates content-hashed asset names such as:

```txt
assets/index-a1b2c3.js
assets/index-d4e5f6.css
```

Those assets can be cached for a long time because their filenames change when their content changes. `index.html` must not be cached for a long time because it points to the current asset filenames.

Keep the default behavior on **CachingDisabled**, then add an ordered behavior:

1. Open the distribution and go to **Behaviors**.
2. Create a behavior with path pattern `/assets/*`.
3. Use the same private S3 origin.
4. Set viewer protocol policy to **Redirect HTTP to HTTPS**.
5. Allow only **GET, HEAD**.
6. Enable compression.
7. Select the AWS managed **CachingOptimized** cache policy.
8. Do not attach the SPA rewrite function to this `/assets/*` behavior.
9. Save and wait for deployment.

This ensures that application routes and `index.html` stay fresh while hashed Vite assets use the CDN efficiently.

Optionally attach the AWS managed **SecurityHeadersPolicy** response headers policy to both behaviors. This adds generally useful browser security headers. Test the application after enabling it. Add a strict custom Content Security Policy only after inventorying all script, style, image, API, WebSocket, and editor sources used by the dashboard; an incorrect CSP can break the application.

## Step 8: Perform the First Manual Upload

The AWS CLI method is recommended because it is repeatable, applies correct cache metadata, and removes obsolete files.

Rebuild immediately before uploading:

```powershell
npm ci
npm run build
```

Confirm that `dist/index.html` and `dist/assets/` exist.

Upload non-HTML root files with a moderate cache time:

```powershell
aws s3 sync dist/ s3://YOUR_BUCKET_NAME/ --delete --exclude "index.html" --exclude "assets/*" --cache-control "public,max-age=3600"
```

Upload content-hashed Vite assets with long-lived immutable caching:

```powershell
aws s3 sync dist/assets/ s3://YOUR_BUCKET_NAME/assets/ --cache-control "public,max-age=31536000,immutable"
```

Upload `index.html` last with no browser caching:

```powershell
aws s3 cp dist/index.html s3://YOUR_BUCKET_NAME/index.html --content-type "text/html; charset=utf-8" --cache-control "no-cache,no-store,must-revalidate"
```

The first command deliberately excludes `index.html` and `assets/*`; the next two commands manage them with more suitable caching rules. The assets command deliberately does not use `--delete`. Users with an already-open page and rollback builds can still reference files from the previous release. Periodically remove old hashed assets only after the retention period chosen for rollback and active sessions; an S3 lifecycle rule for the `assets/` prefix is safer than deleting them during a release.

Inspect the deployed files:

```powershell
aws s3 ls s3://YOUR_BUCKET_NAME/ --recursive
```

Create a CloudFront invalidation so edge locations stop serving any previous release:

```powershell
aws cloudfront create-invalidation --distribution-id YOUR_DISTRIBUTION_ID --paths "/*"
```

The wildcard is one invalidation path. AWS includes a monthly allowance and charges after the allowance is exceeded, so avoid unnecessary repeated invalidations.

### Console-Only Upload Alternative

If AWS CLI cannot be used:

1. Build locally with `npm run build`.
2. Open the private S3 bucket and choose **Upload**.
3. Upload the contents inside `dist/`, not the `dist` folder itself.
4. Confirm that `index.html` is at the bucket root and `assets/` is beside it.
5. Open the CloudFront distribution, go to **Invalidations**, create an invalidation, and enter `/*`.

The Console method works, but it is easier to leave stale files or apply inconsistent cache metadata. Prefer the CLI commands for normal releases.

## Step 9: Point the Domain to CloudFront

Do this only after:

- The ACM certificate is **Issued**.
- The CloudFront distribution contains `admin.amuslimmatchmaker.com` as an alternate domain name.
- The distribution status is **Enabled/Deployed**.
- The first frontend build has been uploaded.

### Route 53 DNS

1. Open **Route 53**.
2. Open the public hosted zone for `amuslimmatchmaker.com`.
3. Choose **Create record**.
4. Set record name to `admin`.
5. Set record type to **A**.
6. Enable **Alias**.
7. Route traffic to **Alias to CloudFront distribution**.
8. Select the dashboard distribution and create the record.
9. Create an **AAAA Alias** to the same distribution if IPv6 is enabled on CloudFront.

### Cloudflare or Another DNS Provider

Create this record:

```txt
Type: CNAME
Name/Host: admin
Target/Value: d123example.cloudfront.net
TTL: Auto or 300
```

Replace the target with the actual CloudFront distribution domain.

If using Cloudflare, initially set the record to **DNS only** rather than proxied. This avoids placing Cloudflare TLS/caching in front of CloudFront while the AWS configuration is being verified. Proxying can be evaluated later as a separate architectural decision.

Remove or replace any conflicting existing `admin` A, AAAA, or CNAME record. Do not change the root domain, `www`, API, email, or other unrelated DNS records.

Verify DNS from PowerShell:

```powershell
Resolve-DnsName admin.amuslimmatchmaker.com
```

## Step 10: Configure the Backend for the New Frontend Origin

The browser will call:

```txt
Frontend origin: https://admin.amuslimmatchmaker.com
API origin: https://api.amuslimmatchmaker.com
```

These are different origins, so the API must explicitly allow this frontend origin through CORS:

```txt
https://admin.amuslimmatchmaker.com
```

Do not configure CORS as `*` for authenticated admin endpoints. Allow only required origins, headers, and HTTP methods. The API must permit headers actually used by the dashboard, including `Authorization` and `Content-Type` when applicable.

If authentication uses cookies, also verify:

- CORS credentials are enabled on the API.
- Cookies use appropriate `Secure`, `HttpOnly`, `SameSite`, domain, and path attributes.
- The frontend opts into credentials where required.
- CSRF trusted origins include `https://admin.amuslimmatchmaker.com` if the backend framework requires it.

This dashboard currently sends bearer tokens in the `Authorization` header for authenticated API requests, so the backend CORS configuration must allow that header.

## Step 11: Verify the Production Deployment

Test both URLs:

```txt
http://admin.amuslimmatchmaker.com
https://admin.amuslimmatchmaker.com
```

The HTTP URL must redirect to HTTPS. The HTTPS URL must have a valid certificate for `admin.amuslimmatchmaker.com` with no browser warning.

Complete this checklist:

- [ ] The login page loads over HTTPS.
- [ ] HTTP redirects to HTTPS.
- [ ] The certificate covers `admin.amuslimmatchmaker.com`.
- [ ] No mixed-content warnings appear in DevTools.
- [ ] Login reaches `https://api.amuslimmatchmaker.com/api`.
- [ ] Authenticated API calls succeed without CORS errors.
- [ ] `/users`, `/matches`, `/settings`, and other routes load.
- [ ] Refreshing a nested route such as `/users/123` still loads the React application.
- [ ] A missing asset such as `/assets/definitely-missing.js` does not return `index.html`.
- [ ] JavaScript and CSS responses have the correct content types.
- [ ] S3 Block Public Access remains enabled.
- [ ] Direct anonymous S3 object access is denied.
- [ ] CloudFront serves the same object successfully.
- [ ] No `.env`, credential, or private file was uploaded.

Expected cache behavior:

```txt
index.html: no-cache/no-store
assets/*: public, max-age=31536000, immutable
```

CloudFront may initially report a cache miss. Subsequent requests for the same hashed asset should be eligible for a cache hit.

## Routine Manual Deployment Workflow

For every approved production release:

1. Confirm `.env.production` points to the intended production API.
2. Confirm the AWS CLI is using the intended account.
3. Build from the project root.
4. Upload root files, assets, and `index.html` with the correct caching rules.
5. Invalidate CloudFront.
6. Test login and at least one nested-route refresh.

Commands:

```powershell
aws sts get-caller-identity
npm ci
npm run build
aws s3 sync dist/ s3://YOUR_BUCKET_NAME/ --delete --exclude "index.html" --exclude "assets/*" --cache-control "public,max-age=3600"
aws s3 sync dist/assets/ s3://YOUR_BUCKET_NAME/assets/ --cache-control "public,max-age=31536000,immutable"
aws s3 cp dist/index.html s3://YOUR_BUCKET_NAME/index.html --content-type "text/html; charset=utf-8" --cache-control "no-cache,no-store,must-revalidate"
aws cloudfront create-invalidation --distribution-id YOUR_DISTRIBUTION_ID --paths "/*"
```

The `--delete` option on the first command removes obsolete non-asset root files. It excludes `index.html` and `assets/*`. Old hashed assets are retained intentionally so active sessions and rollbacks do not break. Always confirm `dist/` is a complete, successful build before running these commands.

## Recommended IAM Permissions for the Deployer

Do not use the AWS root account for deployments. Use an IAM identity with permission only to update this bucket and invalidate this distribution.

An example identity policy is:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ListDeploymentBucket",
      "Effect": "Allow",
      "Action": [
        "s3:ListBucket",
        "s3:GetBucketLocation"
      ],
      "Resource": "arn:aws:s3:::YOUR_BUCKET_NAME"
    },
    {
      "Sid": "ManageDeploymentObjects",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject",
        "s3:DeleteObject"
      ],
      "Resource": "arn:aws:s3:::YOUR_BUCKET_NAME/*"
    },
    {
      "Sid": "InvalidateDashboardDistribution",
      "Effect": "Allow",
      "Action": "cloudfront:CreateInvalidation",
      "Resource": "arn:aws:cloudfront::YOUR_AWS_ACCOUNT_ID:distribution/YOUR_DISTRIBUTION_ID"
    }
  ]
}
```

This IAM identity policy is separate from the S3 bucket policy used by CloudFront OAC. The deployer writes files; CloudFront only reads them.

## Rollback Procedure

Before releasing, retain the previous known-good `dist/` artifact if possible.

To roll back:

1. Locate or rebuild the previous known-good version.
2. Upload it using the same three S3 commands.
3. Create a CloudFront invalidation for `/*`.
4. Verify login and nested routes.

If S3 Versioning is enabled, previous object versions can also be restored. A Vite release includes `index.html` and its matching hashed assets; restoring only `index.html` can break the site if its referenced assets are unavailable.

## Troubleshooting

### CloudFront Returns Access Denied

Check all of the following:

- The CloudFront origin is the regular S3 bucket endpoint, not the website endpoint.
- The OAC is attached to the origin.
- The bucket policy permits the CloudFront service principal.
- The bucket policy `AWS:SourceArn` contains the correct distribution ID and account ID.
- `index.html` exists at the S3 bucket root.
- The default root object is `index.html` without a leading slash.

Do not solve this by making the bucket public.

### The Domain Shows a Certificate Error

Check:

- The ACM certificate is in `us-east-1`.
- Certificate status is **Issued**.
- The certificate contains `admin.amuslimmatchmaker.com`.
- The certificate is attached to the correct CloudFront distribution.
- The distribution alternate domain name contains `admin.amuslimmatchmaker.com`.
- DNS points to that exact distribution.

### DNS Does Not Resolve or Goes to the Wrong Site

Check for an old or conflicting `admin` A, AAAA, or CNAME record. Confirm that the target is the correct `d...cloudfront.net` hostname. Allow time for the previous TTL to expire.

### Refreshing a React Route Fails

Confirm that `amm-admin-spa-rewrite` is published, associated with the default behavior on the **Viewer request** event, and rewrites extensionless routes to `/index.html`. Do not associate it with `/assets/*`.

### The Page Loads Old Code

Check:

- The build completed before upload.
- The correct S3 bucket was updated.
- `index.html` was uploaded last with no-cache metadata.
- An invalidation was created for the correct distribution and completed.
- Browser cache or a service worker is not serving an old version.

### The Browser Receives HTML Instead of JavaScript

This usually means a missing asset request was rewritten to `index.html` or stale HTML references a deleted asset.

- Verify that the SPA function does not rewrite paths containing a file extension.
- Re-upload the complete matching `dist/` build.
- Invalidate `/*`.
- Do not restore only `index.html` during rollback.

### API Calls Fail with CORS Errors

The fix belongs on the API, not S3 or CloudFront. Add the exact frontend origin `https://admin.amuslimmatchmaker.com`, and allow the required methods and headers, especially `Authorization` and `Content-Type`. Do not use a wildcard origin for authenticated admin traffic.

### API Calls Go to the Wrong Backend

Confirm `.env.production` contains the correct `VITE_API_BASE_URL`, then rebuild and redeploy. Changing `.env.production` without rebuilding does not change deployed JavaScript.

## Costs and Operational Notes

This setup can incur charges for:

- S3 storage and requests
- CloudFront traffic and requests
- CloudFront invalidations beyond the current free allowance
- Route 53 hosted zone and DNS queries if Route 53 is used
- Optional AWS WAF usage
- Additional S3 storage for retained object versions

ACM public certificates used with integrated AWS services do not have a separate certificate charge, but always verify current AWS pricing. Set an AWS Budget and billing alert if the account does not already have one.
